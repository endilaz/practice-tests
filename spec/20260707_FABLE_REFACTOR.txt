● This is a solid project — the README is genuinely excellent, the security
  model (RLS-authoritative, server-side scoring, answers never sent to the
  client) is thought through, and the importer handles impressively gnarly
  real-world input. The improvements I'd suggest are mostly about durability and
  maintainability rather than features. Here's what I'd prioritize:

  High value

  1. Check your database schema into the repo. Right now generate_test(),
  submit_test(), all RLS policies, triggers, and table definitions live only in
  the Supabase dashboard. If the project is ever migrated, the dashboard state
  gets fat-fingered, or you want a second environment, there's no source of
  truth. The Supabase CLI (supabase db pull + a supabase/migrations/ folder)
  fixes this in an afternoon and is the single biggest resilience win available.
  It also unlocks running a local Supabase instance for development instead of
  testing against production data.

  2. Add tests for the study-guide parser. You have zero automated tests across
  8,400 lines, and the manual checklist in the README is doing that job. You
  don't need to test everything — but DocxImportStudyguides.tsx (1,732 lines) is
  regex-heavy parsing logic that you've already broken and re-fixed several
  times across commits ("relaxed regex so that 2017-2020 guide is imported
  correctly"). Extract the pure parsing functions (answer-key matching,
  orphaned-number recovery, packed-entry splitting) into a src/questions/parse/
  module and pin them with Vitest cases built from the actual weird inputs
  you've documented ("Intr oduction to Parliamentary Pr ocedure", 5) C15) A26) 
  A, etc.). Vitest is a small add on top of Vite, and every future regex tweak
  stops being a regression risk.

  3. Fix the known bugs before adding features. Your last two commits mention
  "feedback still not working" and the rosha practice-mode bug, and spec/TODO.md
  is one truncated sentence ("fix practiceshell 318: letter is randomized
  but…"). Looking at PracticeShell.tsx:318, the incorrect-answer message says
  "The correct answer is highlighted" — if the letter/highlight mapping is off
  against the randomized displayed_choices_order, that's likely the mismatch.
  Worth pinning these down while the context is fresh; I'm happy to dig into
  either one.

  4. Add ESLint + a lint script. There's no linting at all. typescript-eslint
  with eslint-plugin-react-hooks would catch the exact class of bug this
  codebase is most exposed to — stale closures and missing hook dependencies.
  You've already had to work around that with the responsesRef pattern in
  TestShell; the hooks lint rule catches the cases you haven't noticed yet.

  Worth doing

  5. Split the three giant files. DocxImportStudyguides.tsx (1,732),
  QuestionsAdmin.tsx (1,292), and TestShell.tsx (1,066) each mix data logic,
  state, and UI. For TestShell specifically, extracting the persistence layer
  (autosave, optimistic writes, refs) into a useTestAttempt hook would make the
  component readable and let PracticeShell share it instead of diverging.

  6. Clean up dead code. src/topics/useTopics.ts, src/topics/topic.schema.ts,
  and src/questions/useQuestions.ts are empty files (the README documents them
  as real, which will mislead future-you). src/questions/DocxImport.tsx (607
  lines) looks superseded by DocxImportStudyguides.tsx — if so, move it to
  deprecated/ or delete it. Also either adopt React Query or uninstall it; an
  installed-but-banned dependency is the worst of both.

  7. Tighten .gitignore. It contains *. (matches nothing useful — likely a typo)
  and *.txt, which will silently ignore any text asset you ever want to commit.
  token.* also matches more than intended.

  8. Add a catch-all route and an error boundary. The router has no path: '*' —
  unknown URLs render nothing. A small 404 route plus React Router's
  errorElement on the root would also stop a render error in TestShell from
  white-screening a student mid-test, which is your worst-case UX.

  Operational / housekeeping

  9. Move the repo out of OneDrive. node_modules and .git under OneDrive cause
  sync churn, file-lock flakiness, and slow installs on Windows. Either move to
  C:\dev\ or exclude the folder from sync.

  10. Guest-account accumulation. Anonymous sign-ins (/guest) create a permanent
  auth.users row per visit. Over time that's unbounded growth in users,
  attempts, and responses. A scheduled cleanup (Supabase pg_cron deleting
  anonymous users older than N days, cascading their attempts) is cheap
  insurance.

  11. Deployment + CI. There's no .github/workflows and no hosting config. Even
  a minimal GitHub Action running npm run build (which already includes tsc 
  --noEmit) on push would catch type errors before they land on main. When you
  deploy, remember the SPA rewrite rule (/* → /index.html) since you're using
  createBrowserRouter.

  If I were sequencing this: migrations (#1) and the bug fixes (#3) first, then
  Vitest + parser extraction (#2) since the importer is where you keep
  iterating, then lint/cleanup as background work. Want me to start on any of
  these?
